# 07A 接口草案

状态：待团队确认。可执行定义在 `confidence_a/contracts.py` 与 `confidence_a/contracts_v02.py`，JSON Schema 在 `schemas/`。未知字段拒绝。新增字段要升版本。

`score_snapshot(snapshot, policy=None)` 按 `schema_version` 分派。0.1 与 0.2 的策略文件也不能混用。

## 0.2 输入：评分投影，不是第二套裁判

入口消费证据链 B 的快照声明和 Loop 的剪枝、停止、补证记录。不要把评测 gold、`critical_conditions_annotated` 之类的离线计数放进单例输入；多出来的字段会被拒绝。

绑定字段：`task_id`、`run_id`、`graph_version`、`answer_version`。`answer_binding` 必须与这四项相同，否则 `ContractError`。

| 字段 | 含义 |
|---|---|
| recommendation | `eligible` / `ineligible` / `undetermined`。业务结果，由上游给出。 |
| workflow_status | `checking` / `needs_clarification` / `escalated` / `completed`。除 checking 外必须有 `stop_reason`。 |
| baseline_checks | 独立必查清单。`built=false` 表示应有义务没建入。`COMPLETE` 不能和缺建同时出现。 |
| claims | 答案主张。`mapped=false` 时不能再引用义务。影响答案的未映射主张会阻断。 |
| obligations | 已识别条件。四态沿用 SUPPORT / REFUTE / UNKNOWN / CONFLICT。另有 `criticality` 和可选 `prune`。 |
| clauses | 已发现条款。`expanded=false` 表示未展开，不能当成条件已齐。 |
| relations | `review_status=proposed/accepted/rejected/unresolved`。这不是四态。 |
| changes | 结构增量。历史变化可以指向旧图版本；当前卡的版本以绑定字段为准。 |
| scope_declaration | 至少一条已知限制。`status=unclear` 且 `affects_answer=true` 时阻断。 |
| evidence | `evidence_id`、`source_type`、`citation`。引用必须能落到这里。 |

关系类型沿用共同口径：`depends_on/supports/refutes/applies_to/exception_of/overrides/derived_from`。

剪枝记录只接受 `source=loop|checker_b`，并且要有 `record_id` 和 `reason`。关键、必查或 must-verify 的未决项不能剪。

补证动作如果上游提供了，就原样出现在成绩单里。没有提供时，成绩单写明评分器不编造工具名。

原因码不做封闭词表。`ACCESS_DENIED`、`PAGINATION_INCOMPLETE`、`BUDGET_STOP` 会被认成工具限制原因；`MISSING_FROM_GRAPH` 会写进必查阻断说明。其他原因码仍保留在原文里。

## 0.2 输出

机器定义见 `schemas/scorecard_v02.schema.json`。样例在 `examples/v2/`。

成绩单至少包含：

- 绑定版本、`version_consistent`、`scoring_version`
- `recommendation` 与 `workflow_status`
- `level`、`level_code`、`level_reasons`
- 五个分项的分子、分母和比例
- `claim_refs`、`condition_refs`、`evidence_refs`
- `graph_build_risks`、`residual_gaps`、`reservations`
- `repair_actions`、`structure_changes`、`advice_change_notes`
- `stop_reason`、`human_review_order`、`scope_declaration`
- `score`、`raw_design_score`、`display_score_suppressed`
- 固定声明：这不是图完整性，也不是答案概率

`render_scorecard_markdown` 把这些字段收成可读文本，不新增结论。08B 应优先读 JSON。版本不一致时不要把旧卡和一张新答案拼成最终页；调用方应先拿到同一组绑定版本再评分。

策略文件 `policy.graph.demo.json` 只有一项演示开关：硬门槛失败时是否隐藏设计分。默认隐藏。状态在团队确认前保持 `PROVISIONAL`。

## 0.1 输入输出

0.1 仍是 Checker 义务投影：`checker_decision`、`process_state`、`obligations`、`evidence`。字段表和三个样例没有改语义。Schema 仍是 `schemas/snapshot.schema.json` 与 `schemas/scorecard.schema.json`。

0.1 使用 `RECOMMEND_COMPENSATION` / `DO_NOT_RECOMMEND` / `UNDETERMINED` 和 `RUNNING` / `COMPLETED` / `ESCALATED`。0.2 改用共同口径的 recommendation 与 workflow_status。评分器不猜测这两套枚举的对应关系，避免把旧快照翻译成「必查已完成」。

## 错误

缺字段、枚举错误、悬空引用、版本不一致、缺建却标 COMPLETE、关键项带剪枝、0.1 确定结论与必要缺口冲突，都抛 `ContractError`。这是契约问题，不是一张低分成绩单。命令行返回码 2，并且不写输出文件。
