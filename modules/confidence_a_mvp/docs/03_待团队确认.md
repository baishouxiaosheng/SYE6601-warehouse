# 待团队确认的业务规则与接口决策

下面两项都还不是正式业务事实：0.1 的等权和 49 分上限，0.2 的等权设计分、隐藏总分开关，以及本文列出的暂定处理。样例是合成联调数据，不是 01A 标准答案，也不是实验结果。

## 业务定义仍由 01A 和产品经理确认

0.1 清单里的 B01–B11 继续有效：原子命题、必查、来源组合、空结果、冲突、时间和来源权威都还没有签成正式规则。0.2 只消费上游已经声明的必查和四态，不补这些定义。

## 0.2 暂定处理

这些选择是为了让反例有确定行为。团队否定任何一条，都应该改评分版本，而不是改一次样例分数。

| ID | 暂定 | 为什么先这样 | 需要谁确认 |
|---|---|---|---|
| G01 | 证据不足时默认不展示设计分，而不是沿用 49 分上限 | 避免图内高完成率看起来像高可靠 | 产品经理、08B |
| G02 | 上游给出确定建议但硬门槛失败时，0.2 出卡并禁止展示；0.1 仍报错 | 成绩单要暴露矛盾，同时不改写业务结果 | 02B、08B |
| G03 | 关键关系只要还是 proposed 或 unresolved 就阻断 | 未接纳不等于已审核通过 | 02B |
| G04 | 非关键未决项没有 Loop/B 剪枝记录时阻断，不升成「保留」 | 评分器不能自己说它无关 | 03A、02B |
| G05 | 有剪枝记录的非关键项只保留，不自动 escalated | 修正说明要求不要一律升级 | 03A |
| G06 | 必查 `NOT_APPLICABLE` 且有说明时算覆盖；`built=false` 且 `COMPLETE` 直接报错 | 缺建和「查过并确认不适用」不是同一件事 | 02B、产品经理 |
| G07 | 空的必查清单、空主张或空条件分母不能满分 | 否则漏报会变成 100 分 | 01A、02B |
| G08 | 不影响答案的未映射主张降为保留项，不静默忽略 | 主张覆盖要看得见 | 01A、08B |
| G09 | 设计分把五个分项的分子分母直接相加 | 等权只是演示，不代表风险相同 | 产品经理 |
| G10 | 403、分页未完、预算停止只在它们被写成缺口原因时阻断 | 不把无关历史失败扩大成整单无效 | 03A、04B |
| G11 | checking / needs_clarification / escalated 都不展示确定建议 | 流程未完成 | 03A、08B |
| G12 | 0.1 枚举不自动映射成 eligible / ineligible | 缺少的必查声明无法可靠翻译 | 全组 |
| G13 | 原因码除三个工具限制外不封闭 | 上游词表还没冻结 | 02B、03A |
| G14 | 复核顺序用固定优先级，不是收益模型 | 先让阻断项排在保留项前面 | 08B |
| G15 | 范围声明至少写一条已知限制 | 否则成绩单无法展示范围边界 | 01A |

另外还没有确认：真实补偿场景里哪些检查算基础必查；`criticality`、`required_for_decision`、`must_verify` 三者不一致时以谁为准。现在是任一为真都按关键缺口处理。

## 首次联调最少要什么

一条 DYN-01：合同返回前后的两份 0.2 投影，包含必查结果、新条件、关系审核、结构变化和同一组版本号。02B 给出四态和缺建，03A 给出剪枝或停止原因，08B 按等级而不是按绿色总分展示。在这之前可以用 `examples/v2/`。
