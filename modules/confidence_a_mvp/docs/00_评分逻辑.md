# 评分逻辑与模块边界

成绩单描述的是**已声明范围内的证据与过程质量**。它不证明图完整，不证明已经发现全部规则，也不是答案正确概率。不存在无条件的「完全可靠」。

评分不重新判断四态，不读取评测 gold，也不调用模型给整份答案打分。模板说明只复述已经记录的原因。

## 两个可评分版本

| schema_version | 用途 |
|---|---|
| `0.1-draft` | 已合并的义务快照。继续按等权查明比例和 49 分演示上限出卡。 |
| `0.2-draft` | 动态建链投影。先硬门槛，再给等级和设计分。 |

`0.1-draft` 不会自动升级。它没有必查清单、主张映射、关系审核、剪枝记录和范围声明；自动补这些字段就会把「没声明」说成「已覆盖」。`adapt_v01_to_v02` 会明确抛出 `ContractError`。未知版本同样拒绝。

## 0.2 先硬门槛，再等级

等级只有三个：

| 等级 | 代码 | 何时 |
|---|---|---|
| 证据不足 | `INSUFFICIENT_EVIDENCE` | 存在任一硬门槛 |
| 附保留说明 | `WITH_RESERVATIONS` | 没有硬门槛，但有上游已说明的保留项 |
| 已建模范围内证据充分 | `SUFFICIENT_WITHIN_SCOPE` | 硬门槛和保留项都没有 |

硬门槛阻断受影响的确定建议，**包括无依据的否定建议**，不只阻断「建议补偿」。`recommendation` 仍保留上游原值，`may_present_definitive_decision=false`，并在上游给出 eligible 或 ineligible 时标记 `upstream_recommendation_blocked`。流程状态也不由评分器改成 escalated。

当前硬门槛：

- 关键、`required_for_decision` 或 `must_verify` 的条件仍是 UNKNOWN / CONFLICT。
- 条件适用性为 UNDETERMINED。
- 必查项未完成。缺建（`built=false`）算未完成，不能因为其他节点都是 SUPPORT 就满分。
- 没有必查清单、没有已识别主张，或没有进入分母的条件。空清单不是 100%。
- 关键语义关系为 unresolved，或关键关系仍是 proposed、尚未接纳。
- 关键条款已发现但未展开。
- 影响答案的范围不明。
- 非关键缺口、未展开条款或未决关系没有 Loop / 证据链 B 的「不影响本次结论」记录。评分器不自行认定无关。
- 影响答案的主张无法映射到条件检查。
- 403（`ACCESS_DENIED`）、分页未完（`PAGINATION_INCOMPLETE`）或预算停止（`BUDGET_STOP`）如果写在上述缺口的原因码里，作为该缺口的原因展示。没有挂到缺口上的历史工具失败不会单独阻断。

可展示确定建议还要求：没有硬门槛、`workflow_status=completed`，且业务结果是 eligible 或 ineligible。checking、needs_clarification、escalated 都不展示确定建议。

非关键、非必查、且带有 `prune.source=loop|checker_b` 的残留进入保留项。等级为「附保留说明」，可以保留上游建议，但不自动升级。关键项、程序必查项不能带剪枝记录，否则 `ContractError`。

有充分证据证明不具备资格时，允许「已建模范围内证据充分」的 ineligible。SUPPORT 和 REFUTE 都算已判定。

## 0.2 分项与设计分

设计分只在有定义的计数上合并，必须和等级、分项、硬门槛一起看。

| 分项 | 分子 / 分母 |
|---|---|
| 基础必查覆盖 | 必查中 COMPLETE 或已声明 NOT_APPLICABLE 的项 / 必查项。缺建算未完成。 |
| 答案主张覆盖 | 已映射到现存条件的主张 / 已识别主张。未映射项另列。 |
| 已识别条件证据完成 | 适用且已判定（SUPPORT 或 REFUTE）的条件 / 未排除的已识别条件。 |
| 材料展开与语义审核 | 已展开条款 + 已审核完毕的关键关系 / 条款数 + 关键关系数。未展开不算完成。 |
| 来源适用与查询完整 | 上游 checks 为 true 的次数 / 五项 checks × 进入分母的条件数。 |

分母为 0 的分项不参与合并，也不当成满分。设计分 = `100 × 各有效分子之和 / 各有效分母之和`，等权是待确认的演示口径。

证据不足时默认 `score=null`、`display_score_suppressed=true`，同时保留 `raw_design_score` 供审计。这样图内完成率很高时也不会出现一个可被读成「高可靠」的绿色总分。把策略改成不隐藏分数，也只是把原始设计分露出来，等级和门槛不变。

辅助证据条数不进入公式。多几条旁证不能抵消关键 403 或未完成分页。

## 0.2 成绩单还复述什么

- 绑定的 `task_id/run_id/graph_version/answer_version`。与 `answer_binding` 不一致就拒绝评分。
- 业务结果与流程状态，两者分开。
- 主张、条件、证据引用。
- 建链风险、残留缺口、保留项。
- 上游补证动作和结构变化。建议如何变化，只复述变化记录里的 `from_recommendation/to_recommendation` 和当前四态。
- 停止原因、优先复核顺序、范围声明、评分版本 `graph-risk-0.2.0`。

优先复核顺序是固定优先级：缺必查、仍开放的结构增量、关键条件、适用性不明、关键未决关系、关键未展开、范围不明、未映射主张、未说明残留，最后才是保留项。这不是业务紧急度模型。

DYN-01 的演示是同一任务的两张卡：合同返回后新增「故障后 24 小时内提交工单」。工单未取时是证据不足；取回并经 B 标成 SUPPORT 后重算。两张卡的图版本和答案版本各自一致，并且彼此不同。

## 0.1 仍保留的行为

0.1 只看已建模义务。原始分是查明数 / 分母，阻断时展示分不超过 `blocked_score_cap`（演示默认 49）。Checker 给出确定结论但硬门槛失败时，0.1 抛出 `ContractError`，不改写结论。0.2 改为出卡并禁止展示该确定建议，因为成绩单的职责就是把这个矛盾露出来。

0.1 的适用性、SUPPORT/REFUTE 引用要求和「非关键未知不必强制拒答」仍然有效。详见三个 `examples/*.snapshot.json`。
