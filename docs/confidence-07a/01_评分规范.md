# 07A 置信度成绩单 v2 · 评分规范

版本：scorecard `07a-scorecard-v2`，policy `2.1.0`（**PROVISIONAL**，待团队确认）。
策略文件：`confidence_07a/policy/scorecard_policy.v2.json`；所有权重、矩阵、词典、门槛都在其中，代码不写死数值。
实现：`confidence_07a/scorecard.py`（`score_run` / `diff_scorecards`），`confidence_07a/expression.py`（措辞分类）。

## 1. 分数是什么、不是什么

- 分数是**基于现有日志的证据审核结果**，不是回答正确的概率。每份成绩单都带 `score_semantics` 字段写明这一点。
- 结论状态（五态）**全部来自上游**：01A 节点的 `evidence_status`，或在明确匹配时来自 02B 的局部检查。07A 不重新判断状态。上游判错的地方（见 §9）由离线评测指标暴露，不在评分层修正。
- 等级只覆盖已建模的条件，不能证明证据图完整或已发现全部适用规则（`scope_note`、`build_risks.scope_statement`）。
- 在线成绩单不读取 gold，不读取《案例说明 md》，也不调用模型。
- 权重和等级线均为暂定值，尚未用独立评估数据校准。

## 2. 输入单位：结论五态与措辞四类

结论状态沿用上游，不改名：

| 状态 | 中文 | 含义 |
|---|---|---|
| SUPPORT | 已支持 | 上游检查认为证据条件满足 |
| REFUTE | 与证据矛盾 | 有可复算的矛盾检查 |
| UNKNOWN | 证据不足 | 证据不足，或**没有任何检查命中而默认未知**（见 §7） |
| CONFLICT | 来源冲突 | 来源或限制冲突 |
| MISSING_RULE | 缺适用规则 | 缺判定所需的规则或授权 |

措辞强度 `expression` 由 07A 根据回答原文判定，规则是确定的（`expression.py`）：

| 措辞 | 含义 | 例（真实回答片段） |
|---|---|---|
| DEFINITE | 确定断言，含审批、放行、可操作类结论 | “可以开机”“库房中未找到 M8 钛合金螺栓” |
| HEDGED | 带推测、预计、可能等限定 | “可能有一定积灰”“预计今天到货” |
| DECLARED_UNKNOWN | 明确说无法确定、待确认、查不到、需人工 | “目前仅凭远程数据无法确定具体原因”“暂时查不到实时物流状态” |
| SCOPED_PARTIAL | 明确限定范围的部分结论 | “当前页面未发现…”“已查白班中班合计…” |

判定顺序：

1. 若适配器已经给出 `expression`（上游字段），直接采用，命中依据为 `upstream_expression`。
2. 按 `policy.expression.precedence` 依次查词典：DECLARED_UNKNOWN、SCOPED_PARTIAL、HEDGED。approval（审批/放行）类结论只能是 DEFINITE 或 DECLARED_UNKNOWN，所以“基本可以开机”仍算确定放行。
3. 若上游 `scope_limited=true`，判为 SCOPED_PARTIAL。
4. 以上都没有命中时，按 `upstream_strength_map` 映射 01A 的 `assertion_strength`，否则默认 DEFINITE。

注意：01A 的 `inference` 主要由“约/大约/应该”触发，而约数并不等于推测（例如“本月电费约 31640 万元”）。因此 `inference` 映射为 DEFINITE，真正的推测词放在 hedge 词典里。

每条结论输出 `expression_hits`，例如 `["HEDGED:可能"]`、`["upstream:approval"]`、`["default"]`，便于复核。

## 3. 三个维度（每个都给分子、分母、值）

分母为 0 时输出 `value: null` 和 `reason`，不输出 0。

### 3.1 证据支持度 `support`

- 分母：措辞属于 DEFINITE、HEDGED、SCOPED_PARTIAL 的结论数，即回答中作出了断言的结论。
- 分子：其中上游状态为 SUPPORT 的条数。
- UNKNOWN 不给半分（v1 给 0.5，这里取消）。DECLARED_UNKNOWN 不计入，单独计数为 `excluded_declared_unknown`。
- `breakdown` 同时列出 REFUTE/UNKNOWN/CONFLICT/MISSING_RULE 的个数。
- 推荐类结论（01A 的 OBL 节点）只有在上游给出前提关联时才计入，状态取前提中最不利的上游状态（只是汇总，不重判）。01A 目前没有这种关联，所以 45 条 OBL 都没有计分，只在 `build_risks.recommendations_unscored` 中披露。

### 3.2 问题回应覆盖度 `coverage`

- 分母：用户目标数。
- 分子：被回应的目标数。“被回应”指该目标有关联结论（DEFINITE/HEDGED/SCOPED_PARTIAL），或关联了 DECLARED_UNKNOWN 结论（明确说明当前无法确定）。
- 每个目标的状态：
  - `ADDRESSED_SUPPORTED`：任一关联的断言结论为 SUPPORT
  - `ADDRESSED_DECLARED_UNKNOWN`：没有 SUPPORT，但有声明无法确定的结论
  - `ADDRESSED_UNSUPPORTED`：有断言结论，但都未获支持
  - `NOT_ADDRESSED`：未回应
- 关联优先用上游信息：`related_goals`、`meta.covers_goals`、`claim→goal` 的 supports/addresses 边。只有当某目标没有任何上游关联结论时，才做词面兜底：计算字符二元组的重叠系数 |A∩B|/min(|A|,|B|)，阈值为 `linkage.min_overlap=0.5`。兜底得到的关联标记为 `linkage_method: "lexical_fallback"`，并计入保留项 Q4 和建链风险。

### 3.3 不确定性表达准确性 `uncertainty`

对每条结论按 (措辞 × 状态) 查 `policy.expression_matrix`，得到分数和判定。分母为全部结论。

| 措辞 \ 状态 | SUPPORT | REFUTE | UNKNOWN | CONFLICT | MISSING_RULE |
|---|---|---|---|---|---|
| DEFINITE | 1 APPROPRIATE | 0 WRONG | 0 OVERCLAIM | 0 OVERCLAIM | 0 OVERCLAIM |
| HEDGED | 0.5 UNDERCLAIM | 0 WRONG | 1 APPROPRIATE | 1 APPROPRIATE | 1 APPROPRIATE |
| DECLARED_UNKNOWN | 0.5 UNDERCLAIM（特例见下） | 0.5 UNDERCLAIM | 1 APPROPRIATE | 1 APPROPRIATE | 1 APPROPRIATE |
| SCOPED_PARTIAL | 1 APPROPRIATE | 0 WRONG | 0.5 OVERCLAIM | 0.5 OVERCLAIM | 0.5 OVERCLAIM |

- 如实说明“无法确定”在这个维度得满分，修正了 v1 把它判为“过于含糊”而扣分的问题。
- SCOPED_PARTIAL×{CONFLICT, MISSING_RULE} 规范没有写明，本版按 ×UNKNOWN 处理（0.5）。
- **特例 `DECLARED_UNKNOWN_SUPPORT_GAP_CONFIRMED`**：01A 在图中确有缺口时，会把“无法确定”类表述判为 SUPPORT，含义是“这句‘证据不足’本身得到支持”（01A `graph.py` `_derive_status`）。这种情况下按 APPROPRIATE 记 1 分。识别依据是 `verdict_reason` 中出现 policy 指定的标记文字。60 条中有 1 处，即 IND-001 CLM-009。
- `breakdown.checked_only` 是参考值，计算时排除了“没有任何 check 命中、默认 UNKNOWN”的结论。主值仍按规范使用全部结论。

## 4. 硬门槛与等级

先判门槛，再汇总分数。等级只有三档，没有“完全可靠”：

| 等级 | 中文 | 条件 |
|---|---|---|
| INSUFFICIENT | 证据不足 | 存在任一阻断项（B1–B5）或严重问题 |
| QUALIFIED | 附保留说明 | 无阻断项，但有保留项 |
| SUFFICIENT_IN_SCOPE | 已建模范围内证据充分 | 无阻断项且无保留项 |

### 4.1 高风险与主结论

`high_risk_basis` 记录一条结论被判为高风险的全部依据，可同时命中多项：

| 依据 | 说明 |
|---|---|
| `lexicon:<词>` | 结论原文命中 `high_risk.lexicon`（安全、放行、启动、开机、吊装、审批、许可、超限、限重、压力、温度、报警、停机、隔离、动火、受限空间、带电等；2.1.0 起加入保险词：赔付、理赔、拒赔、给付、免责、除外、保障范围、承保、等待期、保额、保险金、退保、核保等 20 个） |
| `goal_lexicon:<词>` | 结论关联的目标文本命中词典 |
| `approval_type` | 上游 `assertion_strength=approval`（审批、放行、可操作类） |
| `gap_high:<GAP>` | 上游 HIGH 关键度缺口影响该结论 |
| `sole_goal_main_claim` | 运行只有一个目标，且该结论是它按回答顺序的第一条关联结论 |

主结论 `is_main`：关联到任一目标，或为 approval 类。

### 4.2 阻断项

| 代码 | 条件 | 是否严重 |
|---|---|---|
| B1 | 主结论、高风险、状态 REFUTE | 高风险依据属于 `severe_bases` 时为严重，代码 `SEVERE_CONTRADICTION` |
| B2 | 主结论、高风险、措辞 DEFINITE、状态 UNKNOWN/MISSING_RULE/CONFLICT | 同上，代码 `SEVERE_OVERCLAIM` |
| B3 | 措辞 DEFINITE 且状态 REFUTE，并且未被 B1 覆盖 | 否 |
| B4 | HIGH 缺口影响了某条 DEFINITE 结论 | 否 |
| B5 | DEFINITE 结论依赖不完整证据：缺口类型属于 `incomplete_gap_types`，或检查类型属于 `incomplete_check_kinds`（分页、可用性/超时、筛选未生效）且该检查的结论不是 SUPPORT | 否 |

**严重问题的判定口径（与规范 §4.2 的差异，待团队确认）**：`severe_bases` 默认是 `["lexicon","goal_lexicon","approval_type"]`。如果一条结论只因 `gap_high` 或 `sole_goal_main_claim` 被判为高风险，B1/B2 仍然阻断，但不记为严重问题，也不触发 `high_risk_alert`。原因是：产量、库存这类问题如果按规范字面执行，会在很多单目标运行上触发安全告警，导致告警泛滥。例如 IND-043“产量为4200件”会被判为 B2，但不是严重问题。

任何严重问题都会把等级强制为 INSUFFICIENT，并设置 `high_risk_alert=true`。

### 4.3 保留项

| 代码 | 条件 |
|---|---|
| Q1_UNADDRESSED_GOAL | 目标未回应 |
| Q2_RESIDUAL_UNCERTAINTY | 非 DEFINITE 措辞的结论仍有未解决状态或残留缺口 |
| Q3_OPEN_GAP | 缺口没有被任何阻断项引用（包括 MEDIUM/LOW 缺口） |
| Q4_LEXICAL_FALLBACK | 目标与结论的关联只能靠词面兜底得到 |
| Q5_BUILD_RISK | `gates.qualifying_build_risks` 中列出的建链风险计数大于 0 |
| Q6_OVERCLAIM | DEFINITE 措辞但状态未解决，且没有达到任何阻断条件 |
| Q7_UNDERCLAIM | 证据已支持，但措辞过于保守 |
| Q8_NO_CLAIMS | 没有可评价的结论 |

`review_status=proposed/unresolved` 的计数照常披露，但默认不构成保留项。01A rule 模式下所有结论都是 proposed，如果计入，所有运行都会带保留项，这一项就失去了区分度。

## 5. 综合分

- `overall = Σ(维度值 × 权重) / Σ权重`，只在值不为 null 的维度上归一化。默认权重为 support 0.5、coverage 0.25、uncertainty 0.25（PROVISIONAL）。
- 有阻断项或严重问题时 `overall_display=false`，对外只显示等级和各维度分项。

## 6. 输出字段

08B 已经读取的顶层字段：`rule_version`（等于 policy 版本）、`support_score`、`coverage_score`、`uncertainty_score`（取值 0–1 或 null）、`high_risk_alert`、`scope_note`、`review_sequence`（复核顺序：先严重问题，再阻断项，最后保留项）。

其余字段：`scorecard_version`、`policy_version`、`policy_status`、`policy_sha256`（对 policy 做规范化 JSON 后的 sha256）、`run_id`、`case_id`、`upstream_versions`（graph_version / plan_version / answer_version / answer_sha256）、`grade`、`grade_label_zh`、`blockers[]`、`qualifications[]`、`severe_issues[]`、`dimensions{support,coverage,uncertainty}`（每个维度含 numerator/denominator/value/breakdown/rule/weight）、`overall`、`overall_display`、`claims[]`、`goals[]`、`gaps[]`、`build_risks{}`、`supplement{plan_action_count, executable, needs_confirmation, manual, actions[]}`、`score_semantics`、`notes`、`generated_by`。

每条结论 `claims[]` 的字段：`claim_id`、`text`、`expression`/`expression_hits`、`upstream_strength`、`status`/`status_zh`/`status_source`、`main_basis[]`、`missing_or_conflicting[]`、`gap_ids`、`affected_goals`、`linkage_method`、`actions[]`（含可执行性）、`uncertainty{score,judgement,cell}`、`is_main`、`is_high_risk`、`high_risk_basis`、`severe`、`severe_code`、`blocker_codes`、`review_status`。其中 `main_basis[]` 的每一项都带 `run_id`、`event_id`、`json_path`、`pointer`（RFC6901 风格）和 `excerpt`。

Schema 见 `confidence_07a/schemas/scorecard.v2.schema.json`（draft-07）。输出不含时间戳，同一输入加同一 policy 得到字节级一致的结果。

## 7. 建链风险披露

`build_risks` 包含以下内容：

- `unmapped_sentences`：回答中映射不到任何结论或推荐的句子。没有原始日志时为 null。
- `goals_without_claims`：没有关联结论的目标。
- `goals_lexical_fallback`、`lexical_fallback_links`：靠词面兜底建立的关联。
- `orphan_evidence`：没有任何边的证据节点（可追溯性不足）。
- `claims_without_checks`、`unchecked_default_unknown`：没有任何 check 命中的结论，其状态是“未检查、默认 UNKNOWN”，不是“检查后 UNKNOWN”。
- `review_status`：proposed/unresolved 状态的节点和边的数量。
- `gap_missing_condition_not_node`、`dangling_action_gap_refs`：悬空引用。
- `recommendations_unscored`：未计分的推荐类结论；`b_review_unmatched`：没有叠加上的 02B 检查。
- `scope_statement`：范围声明。
