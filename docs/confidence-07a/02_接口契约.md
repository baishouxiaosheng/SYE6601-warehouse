# 07A 成绩单 v2 · 接口契约

本文说明三件事：从上游（01A 证据图引擎、06B 测试结果、02B 局部检查）读取哪些字段，怎样映射到统一模型 `RunView`（`confidence_07a/model.py`），以及向 08B 输出什么、命令行怎么用。评分和评测只依赖 `RunView`。上游字段改名时，只需要改 `confidence_07a/adapters/` 下的适配器。

## 1. 固定函数签名（规范 §7）

```python
# confidence_07a/adapters/egraph_v1.py
load_run_from_files(graph_path, plan_path=None, log_record=None, method="rule") -> RunView
load_run_from_artifacts(graph: dict, plan: dict | None, log_record=None, method="rule") -> RunView
load_run_from_06b_result(result_path, log_record=None, method=None) -> RunView
load_v1_scorecard(scorecard_path_or_dict) -> dict          # 原样返回 01A v1 成绩单（也接受 06B 结果文件）
iter_output_dir(output_dir, log_path=None, method="rule") -> Iterator[RunView]
# 附加：iter_06b_dir、latest_06b_files、detect_dir_kind、locator_to_pointer
# confidence_07a/logs.py
load_logs(path) -> dict[run_id, record]                   # 支持单对象 / 数组 / {"runs":[...]} / 目录
# confidence_07a/expression.py
classify_expression(text, upstream_strength=None, policy=None) -> (expression, hits)
# confidence_07a/scorecard.py
load_policy(path=None) -> dict

```

## 2. 01A → RunView 字段映射

| RunView 字段 | 01A 来源（graph/plan JSON） | 备注 |
|---|---|---|
| `run_id` / `case_id` | `graph.run_id` / `graph.case_id` | plan 或日志的 run_id 不一致时抛出 ValueError |
| `question` | 日志 `user_question`，缺失时用 `graph.task.question` | |
| `answer_text` | 日志 `ai_answer` | 01A 产物中没有回答原文；不提供日志时为空，并记入 notes |
| `goals[].goal_id/text/question_type` | `graph.goals[].id/text/question_type` | |
| `goals[].upstream_answered` | `graph.goals[].answered` | 该字段由 v1 scorecard 回写，仅供参考，不参与 v2 计分 |
| `claims[]` | `graph.nodes[type=claim]`，按 `meta.order` 排序 | |
| `claims[].status` | `node.evidence_status` | **原样搬运**；不在五态内时按 UNKNOWN 记录并写 notes |
| `claims[].upstream_strength` | `node.assertion_strength` | |
| `claims[].related_goals` | `node.related_goals` ∪ `claim→goal` 的 supports/addresses 边 ∪ `meta.covers_goals`（下标） | 有值时 `linkage_method="upstream"` |
| `claims[].evidence_ids` | 指向该 claim 的 supports/refutes/checks/uses/derived_from 边的源节点（evidence/rule/fact），以及相关 check 的 `evidence_ref` | |
| `claims[].check_ids` | `checks[].affected_claims` 包含该 claim 的检查 ∪ `meta.checks` | |
| `claims[].gap_ids` | `gaps[].affected_claims` 包含该 claim 的缺口 | |
| `claims[].action_ids` | `plan.actions[].target_claims` 包含该 claim 的动作 | |
| `claims[].scope_limited/value/unit/review_status` | 同名节点字段 | |
| `claims[].verdict_reason` | `meta.verdict_reason` | 用于识别 DECLARED_UNKNOWN×SUPPORT 特例 |
| `claims[].raw` | `meta.order/source_span/entities`、`created_by` | |
| 推荐类（OBL） | `nodes[type=obligation]` | 只有存在 depends_on/requires/derived_from 指向 CLM 的边时才转成 claim（状态取前提中最不利的上游状态）；否则进入 `build_risks.recommendations_unscored` |
| `evidence{id→EvidenceRef}` | `nodes[type∈{evidence,rule,fact}]` | `event_id`=`record_id`（或从 locator 解析），`json_path`=`locator`，`raw.pointer`=RFC6901 指针（需要日志才能确定 trace 下标），`has_edges`=该节点是否有边 |
| `checks[]` | `graph.checks[]` | `check_id/kind/status/verdict/category/affected_claims/evidence_ref/locator/expected/actual/detail`；`raw.event_id/pointer` |
| `gaps[]` | `graph.gaps[]` | `id→gap_id`、`type→gap_type`、`criticality`、`description`；`raw.missing_condition/target_source/mandatory` |
| `actions[]` | `plan.actions[]` | `id→action_id`、`action_type/gap_ids/target_claims/tool/known_arguments/pending_arguments/success_criterion/executability/priority` |
| `upstream_versions` | `graph.graph_version`、`plan.plan_version`、日志 `answer_version`（如有）、07A 计算的 `answer_sha256`（前 16 位） | |
| `scope` | `graph.scope_declaration/limitations/changes`，以及 paths 和共同必要条件的计数 | |
| `build_risks` | 适配器统计的原始计数 | `orphan_evidence`、proposed/unresolved 节点和边的数量、`gap_missing_condition_not_node`、`dangling_action_gap_refs`、`recommendations_unscored`、`invalid_upstream_status_claims` |
| `source` | `{method, engine:"01A-egraph", adapter:"egraph_v1", adapter_version, files, log_record_available}` | |

01A 字段名集中写在 `adapters/egraph_v1.py` 的 `_F` 字典里。

### 2.1 06B 结果文件

`results/evidence_rule/<run_id>_<时间戳>.json`：同一 run 取时间戳最大的一份。读取 `output.graph/plan/scorecard`，映射方式同上。`source` 额外记录 `execution_kind/model_called/elapsed_seconds/input_sha256/passed`。`method` 默认取值：`execution_kind` 中含 `rule` 时为 `rule`。

## 3. 02B → 覆盖层（可选，默认关闭）

| 02B 字段（`b_review.local_review`） | 用途 |
|---|---|
| `run_id` | 必须与 RunView 一致，否则不做任何覆盖 |
| `nodes[type=claim].answer_excerpt` | 与 01A 结论原文对齐。明确匹配的条件：规范化后完全相等；或 excerpt 是**恰好一条**结论的子串，长度至少 4，且占该结论长度至少 0.3 |
| `checks[].target/state/reason` | 匹配成功时 `status←state`，`status_source="02B"`，原状态保存在 `raw.status_01A`，并追加一条 `kind="02B_local_check"` 的 CheckView |
| `gaps[].gap_type=MISSING_RULE` + `state=UNKNOWN` | 视为 MISSING_RULE，不会把 01A 的 MISSING_RULE 降成 UNKNOWN |
| `nodes[type=fact]` 的检查、无法匹配或多条候选的检查、对同一结论给出矛盾状态的检查 | 都不覆盖，写入 `notes` 和 `build_risks.b_review_unmatched` |

实测结果：02B 的工业局部检查只覆盖 5 条运行（IND-002/024/030/043/053）。其中 claim 类检查全部能明确匹配，并且与 01A 的状态一致，所以没有发生任何覆盖。fact 类检查（如 `fact:subtotal`）没有对应的回答结论，只做记录。

## 4. 输出（给 08B）

08B `app_final.py` 读取的顶层字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `rule_version` | str | 等于 policy 版本（当前 "2.1.0"） |
| `support_score` / `coverage_score` / `uncertainty_score` | float 0–1 或 null | 等于 `dimensions.*.value` |
| `high_risk_alert` | bool | 存在任一严重问题 |
| `high_risk_alert_text` | str | 告警文字，可直接显示：`CLM-xxx「原文」：原因；…`；无告警时为空串 |
| `scope_note` | str | 范围说明 |
| `review_sequence` | list[str] | claim_id 按复核优先级排列：先严重问题，再阻断项，最后保留项 |

### 4.1 实验指标（给 08B 看板）

- 看板统一读 **`artifacts/experiment_metrics.json`**：顶层是行列表，前 5 个键 `method`、`false_support`、`gap_locate`、`insufficient_as_err`、`note` 与 08B 现有 `load_experiment_metrics()` 一致；另带 `row_type`、`domain`（工业/保险）、`n_runs`、`gold_version`、`status_accuracy`、`requery_param_hit`、`severe_recall`、`severe_false_alarm`。值可能为 null（未运行或分母为 0），看板要显示“未运行”而不是 0。
- 各评测目录下的 `experiment_metrics.json` 是该次评测的原始输出，`experiment_metrics.full.json` 带完整元数据和置信区间。不要读 `artifacts/eval/`（试点 gold，已被团队 gold 取代）。

### 4.2 在线现跑（08B live 模式）

`confidence_07a.eval.runner.run_engine_rule(engine_path, logs, run_ids=None)` 是受支持的公开接口：用 `load_settings({"mode":"rule"}, env={})` 调 01A 引擎，不读 `.env`、不调模型，返回 `run_id → 结果记录`（与 06B 记录同形，含 `output.graph/plan`）。再用 `records_to_runs(records, "rule", logs_by_run)` 得到 RunView，交给 `score_run`；也可直接用 `adapters.egraph_v1.load_run_from_artifacts(graph, plan, log_record=...)`。如果现跑失败，看板应明确显示“现跑失败”，不要静默退回到其他数据却仍标成“07A v2”。

其余字段见《01_评分规范》§6 和 `schemas/scorecard.v2.schema.json`。补证前后对比 `diff_scorecards` 的输出字段为：`grade{before,after,changed}`、`dimensions.*{before,after,delta,before_fraction,after_fraction}`、`claim_transitions[]`、`transition_summary`、`claims_added/removed`、`blockers_added/removed`、`severe_added/removed`、`gaps_added/closed`、`explanation_zh[]`、`versions{before,after}`、`warnings`。结论先按 claim_id 加原文匹配，再按原文匹配；缺口按 (类型, 受影响结论原文, 描述) 匹配，不依赖缺口编号，因为补证后编号可能错位。

## 5. 命令行

在 `deliverable/` 下运行 `python -m confidence_07a ...`；如果需要 `python -I` 隔离模式，用 `python -I tools/run_cli.py ...`。

```
# 单个运行
python -m confidence_07a score --graph <out>/IND-043_graph.json [--plan ...] --log <日志.json> \
    [--b-review <02B industrial_results.json>] --out-json s.json --out-md s.md
# 整个目录（自动识别 01A output/ 或 06B 结果目录）
python -m confidence_07a score-dir --input <01A output 或 06B results/evidence_rule> --log <日志.json> \
    --out artifacts/scorecards_v2/rule [--b-review ...] [--no-md]
# 补证前后对比
python -m confidence_07a diff --before a.json --after b.json --out-json d.json --out-md d.md
# 离线评测（由 confidence_07a.eval.cli.main(argv) 提供；未提供时返回 2 并提示）
python -m confidence_07a eval|variants|report ...
```

`score-dir` 为每条运行写出 `<run_id>.json`、`<run_id>.md`，另写 `summary.csv`，列为 run_id、case_id、method、grade、high_risk_alert、三个维度、overall、计数、阻断代码，以及 v1 基线的等级和三个维度。

辅助脚本（`tools/`）：

- `run_cli.py`：`-I` 模式下的 CLI 启动器。
- `demo_g6_ind043.py`：G6 补证前后演示；`--loopb-shift-file` 读 LoopB 种子记录 `SIM-D-20261113-NIGHT`（合成数据，带来源与 sha256）。
- `gold_agreement.py`：两份 gold 按原文片段对齐，算五态一致率和 Cohen's kappa。
- `run_model_methods.py` / `eval_model_compare.py`：纯模型批量运行（断点续跑）与同口径对照。
- `compare_v1_v2.py`：生成 v1/v2 对比报告。

## 6. 上游字段改名时怎么换适配器

1. 01A 改名：只改 `adapters/egraph_v1.py`。字段名集中在 `_F`，例如 `status: "evidence_status"`、`strength: "assertion_strength"`；结构上的变化（例如 gap 的 `id` 改成 `gap_id`）在 `load_run_from_artifacts` 的对应段落里修改。改完运行 `tests/confidence_07a/test_scorecard_adapters.py`。
2. 新上游（例如 hybrid 模式或 02B 输出完整的逐 claim 四态）：新建 `adapters/<name>.py`，产出同一个 `RunView`；`source.adapter` 填新名字。不要修改 `scorecard.py`。
3. 需要给 `model.py` 增加字段时，必须带默认值，并在本文件记录。本版**没有**修改 `model.py`。用到的扩展信息都放在已有的 `raw` 和 `build_risks` 字典中，包括 `claim.raw.status_01A`、`evidence.raw.pointer`、`check.raw.event_id/pointer` 和 `build_risks.recommendations_unscored`。
4. 运行 `python -m unittest discover -s tests -t .`，确认全部通过（`PYTHONUTF8=0` 下也需要通过）。

## 7. 约束

- 只用标准库，Python ≥ 3.10；所有文件读写都显式指定 `encoding="utf-8"`。
- 不读取任何 `.env`，不调用任何模型或 API。需要跑 01A 引擎时一律使用 `load_settings({"mode":"rule"}, env={})`。
- 在线成绩单不读取 gold，也不读取案例说明 md。
