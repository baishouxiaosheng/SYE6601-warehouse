# 07A 离线评测与指标说明

版本：07a-eval-v1（配置 `confidence_07a/eval/eval_config.v1.json`，状态 **PROVISIONAL**，待团队确认）

> 分数与指标的含义：**基于现有日志的证据审核结果，不是正确概率**。校准表与 ECE 仅为描述性统计。
> 试点 gold 由 AI 起草、尚未人工复核时（`review_status=DRAFT`），评测结果只能用来检验流水线，不能作为方法优劣的结论。

## 1. 范围与边界

- 评测只读：预测（各方法的 `RunView`）、gold 标注（gold.v1）、可选的成绩单（v1 或 v2）。
- **不重新判断证据状态**：上游判错（例如 IND-053 “吊装18吨没有问题”被判 SUPPORT）由 FSR 等指标暴露，不在评测层修正。
- gold 只依据日志 JSON 标注（`source: "json_only"`），评测代码不读取《案例说明 md》。
- 不调用任何模型，不读取 `.env`；仅标准库。运行 01A 引擎时固定 `load_settings({"mode": "rule"}, env={})`。

模块：

| 文件 | 作用 |
|---|---|
| `eval/gold.py` | gold 读取（`load_gold`）、校验（`validate_gold` → errors, warnings）、模板生成（`build_gold_template`） |
| `eval/align.py` | 预测结论 ↔ gold 结论对齐（`align_claims`） |
| `eval/metrics.py` | 指标、bootstrap CI、校准（`evaluate`） |
| `eval/report.py` | `experiment_metrics.json`、`report.md`、`per_claim.csv`、`per_run.csv`（`write_report`） |
| `eval/runner.py` | 01A rule 模式现跑（`run_engine_rule`）、读 06B 结果目录（`load_results_dir`）、编排（`run_methods`） |
| `eval/schema_check.py` | 极简 JSON Schema 校验器（标准库） |
| `schemas/gold.v1.schema.json`、`schemas/experiment_metrics.v1.schema.json` | 两份 schema |

## 2. 使用方式（Python API）

```python
from confidence_07a.eval import run_methods, load_gold, gold_runs, evaluate, write_report

LOG = "工业智能体模拟监控日志_60条.json"
res = run_methods({
    "rule": "industrial_pytest/results/evidence_rule",          # 06B 结果目录（每 run 取最新时间戳）
    "rule_live": {"engine": "path/to/evidence_graph"},          # 离线现跑 01A rule 模式
    # "hybrid": "industrial_pytest/results/evidence_hybrid",    # 需密钥的方法只读已有结果
}, logs=LOG)
gold = gold_runs(load_gold("gold/pilot_gold_v0.json"))
evs = [evaluate(res[m]["runs"], gold, m, scorecards=res[m]["v1_scorecards"], seed=0) for m in res]
write_report(evs, "artifacts/eval", data_version="monitor_log_60", gold_version="pilot_v0")
```

`run_methods` 返回 `method -> {"runs": [RunView], "v1_scorecards": {run_id: dict}, "failures": {run_id: 原因}}`。
处理失败的运行进入 `failures`，在 evaluate 中表现为“无预测”（gold 结论全部计为漏抽），满足需求 §6“记录处理失败原因”。

## 3. gold 格式（gold.v1）

文档对象：`{schema:"gold.v1", gold_version, created_at, notes, runs:[...]}`（读取时也接受纯数组或 `{records:[...]}`）。
每个运行（spec §5.1）：

| 字段 | 说明 |
|---|---|
| `run_id`, `case_id` | 与日志一致 |
| `variant_id` | **扩展**（可选）：受控变体的标注；变体保持原 run_id，以此区分 |
| `annotator`, `annotated_at` | 标注人与时间 |
| `source` | 固定 `json_only` |
| `review_status` | `DRAFT` / `REVIEWED` |
| `goals[]` | `{gold_goal_id, text}` |
| `claims[]` | `{gold_claim_id, pred_claim_id?, answer_span, expression, gold_status, is_high_risk, severe, goal_ids?, evidence_locators:[{event_id, json_path}], rationale}` |
| `gaps[]` | `{gold_gap_id, affects_claims[], gap_type, missing_info, required_params:{tool?, args{...}, success_field?}}` |
| `run_level` | `{answer_has_error, answer_honest_about_limits}` |

- `gold_status` 五态：SUPPORT / REFUTE / UNKNOWN / CONFLICT / MISSING_RULE。`expression` 四类同 scorecard。
- `gap_type` 取 01A 的六类（含 LIMITED_SCOPE）。
- `success_field` 可为字段名字符串（如 `"business_date"`），或 `{字段: 期望值}`（如 `{"business_date": "2026-11-13"}`）。
- `validate_gold(doc, logs)`：schema 校验 + 引用一致性（claim/gap/goal ID、重复运行、event_id 是否在日志 trace 中）。警告：severe 但未标高风险、severe 却 SUPPORT、json_path 不以 `trace[` 开头、DRAFT 运行数。
- `build_gold_template(logs)`：每运行一条空模板，只附 `_question`、`_answer_text`、`_trace_event_ids` 等辅助字段（`_` 开头，不参与评测），**不预填任何判断**，避免把规则或模型输出泄漏进 gold。

## 4. 结论对齐方法

1. **显式映射优先**：gold 结论填了 `pred_claim_id` 且存在 → 直接配对（`method=explicit`）。ID 不存在或已被占用 → 记警告，回落到相似度。
2. **字符相似度**：对 gold `answer_span` 与预测结论文本（`ClaimView.text`，以及适配器保留的 `raw.meta.source_span`）做归一化（NFKC 全角转半角、小写、去千分位逗号、去空白标点），取 `difflib.SequenceMatcher.ratio`。较短串（≥6 字）完整包含于较长串时，分数至少取 `contain_floor=0.8`（原子结论常是回答句子的一部分）。
3. **数值实体一致**：抽取双方数值（`21,500`→`21500`，`2.50`→`2.5`）。双方都有数值且**不相交** → 禁止对齐（`numeric_mismatch`）；部分相交 → 分数乘 `0.5+0.5×Jaccard`。单位不参与：`21500 MPa` 与 `21500 kPa` 可以对齐，单位错误应由状态（REFUTE）体现。
4. **贪心一对一**：所有 ≥ 阈值（默认 0.5）的候选按（分数降序、gold 顺序、预测顺序）依次配对。
5. 未配对 gold = 漏抽；未配对预测 = 多抽。每个运行的对齐细节（含未达标 gold 的最高分与原因）保存在 `evaluate()["alignment"]`，供人工复核阈值。

重复情况：两条 gold 片段相同 → 只有第一条能配上，另一条漏抽；两条预测相同 → 一条配上，另一条多抽。不能按 CLM 序号对齐（01A 会把部分 claim 转为 obligation，ID 不连续）。

## 5. 指标字典

所有比例输出 `{numerator, denominator, value, reason, ci95}`；分母为 0 → `value: null` + `reason`，**不输出 0**。

| 指标 | 定义 | 分子 | 分母 | 为什么 | 陷阱 |
|---|---|---|---|---|---|
| `false_support_strict`（FSR，08B `false_support`） | 错误结论被判为支持 | gold=REFUTE ∧ pred=SUPPORT | 已对齐的 gold=REFUTE | 需求 §6 首要风险：错的说成对的 | 本数据 REFUTE 很少，分母常为 1–3；未对齐的 gold REFUTE 不进分母（见 `excluded_unaligned`），必须和抽取覆盖率一起看 |
| `false_support_broad` | 广义 FSR | gold∈{REFUTE,UNKNOWN,MISSING_RULE,CONFLICT} ∧ pred=SUPPORT | 已对齐的 gold 非 SUPPORT | 也覆盖“证据不足却被判支持”（过度放行） | 与严格版含义不同，报告中分开列 |
| `insufficient_as_err`（IAE） | 证据不足被误判为错误 | gold∈{UNKNOWN,MISSING_RULE} ∧ pred=REFUTE | 已对齐的 gold∈{UNKNOWN,MISSING_RULE} | 过度否定会误伤正常作业、误报警 | pred=CONFLICT 不计入（按 spec 只算 REFUTE） |
| `gap_precision` / `gap_recall` / `gap_f1`（08B `gap_locate`=F1） | 缺口定位 | 命中缺口数（F1 为 2×命中） | 预测缺口数 / gold 缺口数 / 两者之和 | 补查从缺口出发，缺口定位错则补查全错 | 匹配需“受影响的已对齐结论有交集（默认 overlap，可改 exact）且类型相容”；gold 缺口影响的结论若都没对齐，则无法命中；上游重复缺口（IND-030）会拉低精确率 |
| `requery_param_value_hit` | 补查参数定位（键+值） | 相关动作中键存在且值一致的关键参数数 | gold `required_params` 的关键参数总数（tool + args 各键 + success_field） | 需求 §6“补查参数定位准确率” | 值比较做归一化（数值、ISO 时间换算到 UTC、大小写空白）；pending 参数按“文本包含 gold 值”判；`match_value_anywhere=true` 时允许键名不同但值出现在参数文本中（01A 常用中文键名如 `查询窗口`） |
| `requery_param_key_hit` | 补查参数定位（仅键） | 相关动作中出现该键（或 tool 相等） | 同上 | 区分“知道要什么参数”与“参数值也对” | pending 键 + null 值只算键命中 |
| `requery_action_exists` | 动作存在率 | 有至少一个相关动作的 gold 缺口 | 带 required_params 的 gold 缺口 | 区分“没生成动作”和“动作参数错” | 相关动作 = `gap_ids` 含匹配上的预测缺口，或 `target_claims` 与该缺口影响的已对齐结论相交 |
| `status_accuracy` | 五态准确率 | 混淆矩阵对角线 | 已对齐结论数 | 总体一致度 | 规则模式 69% 为 UNKNOWN，准确率受类别分布影响大 |
| `status_macro_f1` | 五态 macro-F1 | Σ 各类 F1 | gold 或 pred 中出现过的类别数 | 抵消类别不平衡 | 未出现的类别不计入；小样本下单类波动很大 |
| `status_kappa` | Cohen's κ | p_o − p_e | 1 − p_e | 扣除偶然一致 | 只出现单一类别时 p_e=1 → null |
| `extraction_coverage` | 结论抽取覆盖率 | 已对齐 gold 结论 | gold 结论 | 防止“少抽结论降低 FSR” | 受对齐阈值影响 |
| `extraction_extra_rate` | 多抽率 | 未对齐预测结论 | 预测结论 | 抽出 gold 未标的结论 | gold 标注粒度不同会造成“伪多抽” |
| `severe_recall` | 严重问题召回 | gold 有 severe 结论 ∧ `high_risk_alert` | gold 有 severe 结论的运行 | 高风险冲突不能被平均分掩盖（需求 §5） | 需要成绩单；v1 成绩单无 `high_risk_alert`，回退为 `severity_flags` 中存在 HIGH（`alert_source` 标明） |
| `severe_false_alarm` | 严重问题误报率 | gold 无 severe ∧ `high_risk_alert` | gold 无 severe 的运行 | 告警过多会被忽视 | 同上 |
| `calibration_ece` | ECE | Σ_b \|Σconf_b − Σcorrect_b\| | 样本数 N | 检查 support_score 能否当概率读 | 样本 = gold 中断言类结论（DEFINITE/HEDGED/SCOPED_PARTIAL）；conf = 所在运行的 support_score（同一运行共享，非独立样本）；correct = gold_status==SUPPORT；默认 5 个等宽分箱；**仅描述性** |

另有：五态混淆矩阵（行 gold，列 pred）、校准表（每箱样本数、平均 support_score、gold SUPPORT 比例）、等级 × `answer_has_error` / `answer_honest_about_limits` 列联表、成本（`elapsed_seconds` 的 n/合计/均值/中位数；模型调用次数取 `run.source.llm_call_count|model_calls`，缺失则注明）。

### 5.1 置信区间

按运行聚类的百分位 bootstrap：每个 gold 运行先算一组可加计数，重抽样运行（有放回，默认 1000 次，固定 `seed`）后重新求和计算所有指标；所有指标共用同一组重抽样索引，结果可复现。分母为 0 的重抽样被丢弃（`ci_valid_resamples` 记录有效次数）。运行数很少时 CI 会退化（如 [0,1] 或单点），只能说明不确定性大。

### 5.2 分层

`run.source` 带 `variant_id`（及 `variant_kind`）时，额外按 `natural` / `variant` / `variant:<kind>` 分层输出指标；无变体信息时输出 `strata_note`。

## 6. 方法对照设计

| 方法名 | 来源 | 本次是否执行 |
|---|---|---|
| `rule` | 01A rule 模式（06B `results/evidence_rule/` 或 `run_engine_rule` 现跑） | 是（离线） |
| `hybrid` | 01A hybrid 模式结果目录 | 只提供入口（需密钥，由 06B 产出后读取） |
| `llm_only` | 纯模型基线结果目录 | 只提供入口 |
| `v1_scorecard` / `v2_scorecard` | 同一组预测 + 不同成绩单 | 是 |

- 方法间比较的预测侧指标（FSR、IAE、缺口、参数、混淆矩阵、抽取）只与图/计划有关。
- 成绩单 v1 vs v2：预测运行相同、只换 `scorecards`（v1 取 06B `output.scorecard`；v2 由 `scorecard.score_run` 生成，键为 run_id）。两者只在 `severe_recall`、`severe_false_alarm`、校准与等级列联表上有差异；结论级指标按构造相同，报告中应说明。
- 所有方法在同一份 gold 与同一 `seed` 下评测；n 小，CI 重叠时不得宣称优劣。

## 7. 受控变体设计（`eval/variants.py`，已实现，结果见“实验结果（试点）”§C）

变体从日志 JSON 生成（需求 §6，spec §5.4）：

| kind | 操作 | 期望变化（expected_effect） |
|---|---|---|
| `drop_evidence` | 删除被某 SUPPORT 结论引用的工具事件 | 目标结论不应再为 SUPPORT |
| `unit_change` | 数值单位改写不换算（kPa→MPa） | 目标结论应变为 REFUTE 或非 SUPPORT |
| `entity_swap` | 设备/产线 ID 替换为另一个 | 目标结论应出现对象不一致（非 SUPPORT） |
| `truncate_page` | 删除分页结果 / 置 has_more | 应出现 INCOMPLETE_RESULT 缺口 |
| `control_noop` | 无关扰动（如重排 JSON 键） | 结论状态与缺口均不变 |

建议接口（供实现者参考，评测侧已按此对接）：

```python
@dataclass
class VariantSpec:
    variant_id: str; base_run_id: str; kind: str
    target_event_id: str | None; json_path: str | None
    target_claim_text: str | None          # 用于在变体输出中对齐目标结论
    expected_effect: dict                  # 如 {"claim_status_not": "SUPPORT"} / {"gap_type_present": "INCOMPLETE_RESULT"} / {"unchanged": True}

def generate_variants(log_record: dict, base_run: RunView | None = None, kinds=None) -> list[VariantSpec]
def apply_variant(log_record: dict, spec: VariantSpec) -> dict          # 返回修改后的日志（run_id 不变）
def evaluate_variants(base_runs, variant_runs, specs) -> dict           # {sensitivity:{比例}, stability:{比例}, rows:[...]}
```

- 变体保持 `run_id = case_id-r1`（01A 校验要求），用 `variant_id` 区分，写入独立目录。
- 变体结果接入评测：适配后的 `RunView.source` 写 `variant_id`、`variant_kind`；若有变体 gold，在 gold 运行中填 `variant_id`；变体成绩单键为 `"run_id#variant_id"`。`evaluate` 会自动分层。
- 敏感性 = 期望变化发生的变体数 / 非 control 变体数；稳定性 = 无变化的 control 变体数 / control 变体数；同样使用 `{numerator, denominator, value, reason}` 格式。

## 8. 校准注意事项

- support_score 是证据审核比例，不是正确概率。ECE 只说明“当前分数与 gold 支持率的偏差”，样本小、同一运行的结论共享同一分数（非独立），不能据此调整阈值或宣称“已校准”。
- 要把分数解释为概率，需要独立、已复核、足够大的评估集，并按运行做交叉验证的保序回归或分箱校准；本版不实现。

## 9. 输出

- `experiment_metrics.json`（schema `experiment_metrics.v1`）：`rows[]` 每方法一行，`false_support`(=严格 FSR)、`gap_locate`(=缺口 F1)、`insufficient_as_err`(=IAE) 为 0–1 或 null，`note` 写明 n、分母和 DRAFT 状态；扩展字段 `metrics`（全部指标含分子分母与 CI）、`metric_mapping`、`strata`、`cost`。写出前做 schema 校验。
- `report.md`：中文，含注意事项、样本量、主要指标表、混淆矩阵、校准表、等级列联表、分层、成本、被判为支持的非支持结论清单（给上游的问题清单）、警告、指标定义。
- `per_claim.csv`：每条 gold 结论一行（含对齐方式/分数、gold/pred 状态、是否 false_support/IAE），多抽的预测结论另起行。
- `per_run.csv`：每运行一行（结论/缺口/参数计数、告警、等级、support_score、耗时）。

## 11. 本版自定的规则（超出 spec，待团队确认）

1. 结论级指标只在已对齐结论上计算，未对齐计入 `excluded_unaligned`。
2. 08B `gap_locate` 取缺口 F1；`false_support` 取严格 FSR。
3. 缺口匹配默认“交集”而非“集合相等”；类型相容组：{MISSING_EVIDENCE, MISSING_DEPENDENCY}、{INCOMPLETE_RESULT, LIMITED_SCOPE}。
4. 补查参数同时报“键命中”和“键+值命中”，主指标为后者；默认允许键名不同的值匹配。
5. 运行级“gold severe” = 该运行任一 gold 结论 `severe=true`。
6. 校准样本为 gold 断言类结论，置信度取运行级 support_score。
7. gold 扩展字段：`variant_id`、`goal_ids`、文档级 `{schema, gold_version, runs}`。

## 实验结果（主结果：05A 团队 gold v2，2026-11-18）

> gold：05A 交付的 `gold/team_v2/industrial_gold_v2.json`（工业 60 条运行、307 个命题）和 `insurance_gold_v2.json`（保险 60 条、444 个命题）。`review_status` 仍为 **DRAFT**，尚未由团队签收，所以以下数字仍是“暂定”。上游为 01A 引擎 rule 模式离线现跑；成绩单 policy 2.1.0。08B 看板统一读 `artifacts/experiment_metrics.json`（顶层行列表，每行带 `domain`、`n_runs`、`gold_version`）。明细：`artifacts/eval_team_gold/`、`artifacts/eval_team_gold_insurance/`、`artifacts/eval_model_compare_team_gold/`。

| 证据不足被误判为错误（IAE） | 0.000 |
| 缺口定位 F1 | 0.147 |
| 补查参数命中（键+值） | 0.065 |
| 五态准确率 | 0.375 |

### E. 纯规则 vs 纯模型小样本对照（真实模型调用）

> 模型：`qwen/qwen3.8-27b`（OpenRouter），入口 `confidence_07a/eval/baselines/llm_judge.py`，批量脚本 `tools/run_model_methods.py`（密钥只从环境变量或一次性密钥文件读取，不落盘）。按用户决定只跑了 33/60 条（全部成功），混合方案未跑。与试点 gold 重合 8 条（IND-002/005/010/015/019/024/027/030），两种方法都用 v2 成绩单，在这 8 条上同口径比较。明细：`artifacts/eval_model_compare/report.md`；对比脚本 `tools/eval_model_compare.py`。

| 指标（n=8 运行） | 纯规则 rule | 纯模型 llm_only |
|---|---|---|
| 五态准确率 | 0.32 | **0.89** |
| 缺口定位 F1 | 0.17 | **0.44** |
| 补查参数命中（键+值） | 0.13 | **0.46** |
| 严重问题召回（运行级） | 0.5（1/2） | **1.0（2/2）**；两者误报都是 1/6 |
| 结论抽取覆盖 | 0.89 | 0.97 |
| 错误结论被判为支持（严格） | **0/7** | 1/9 |
| 证据不足被误判为错误 | 0/8 | 0/8 |

成本：33 条共输入约 5.4 万 token、输出约 36 万 token（含思考），约 0.7 美元；单条平均 70 秒。纯规则单条不到 1 秒、零费用。

怎么读：
- 纯模型在“把回答拆对、判对、指出缺什么、给出补查参数”上明显好于当前纯规则，与需求附录“模型提案 + 代码验证”为主方案的判断一致：**模型适合做提案，代码负责复核**。
- 纯模型出现了 1 条“错误结论被判为支持”，纯规则这 8 条里没有；模型的“支持”仍需代码复核才能放行，这正是混合方案要解决的问题。
- **重要偏差**：试点 gold 也是 AI 起草的，可能与纯模型同偏，模型优势会被高估；n=8，置信区间很宽。正式结论要等 05A 人工复核的 gold，并补跑混合方案（01A 需先让 hybrid 与 llm 两种模式真正分开）。
